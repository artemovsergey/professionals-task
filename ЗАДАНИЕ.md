# Задание отбора

**Компетенция:** Программные решения для бизнеса
**Формат:** отборочный этап, работа в команде до 2 человек допускается

---

## 1. Описание

Нужно разработать небольшое приложение-**планировщик личных задач**. Пользователь заводит задачи, задаёт им сроки, приоритет и категорию, отмечает выполненные, видит сводку по дням.

Это упрощённое и обобщённое задание. В нём нет сложной бизнес-логики, отчётности и интеграций — проверяется умение собрать полный цикл: **база данных → API → несколько клиентов поверх одного API**.

## 2. Что должно работать

### 2.1. База данных

- СУБД: **PostgreSQL** или **MySQL**.
- Минимум две сущности: **пользователь** и **задача**. Третья сущность (**категория**) — по желанию, баллы не влияют.
- Обязательные поля: идентификатор, дата создания, название задачи, описание, статус (выполнена / не выполнена), приоритет (низкий / средний / высокий), дата выполнения, идентификатор пользователя.
- **Ограничения должны быть реализованы средствами SQL**: `NOT NULL`, `CHECK` (например, приоритет только из допустимых значений), внешний ключ на пользователя, уникальность email пользователя.
- Скрипт создания таблиц (`schema.sql` или миграции) обязателен и должен лежать в репозитории.
- ER-диаграмма обязательна (draw.io, DBeaver, Mermaid, PlantUML — на ваш выбор).

Готовый пример: [`db/schema.sql`](db/schema.sql), [`db/README.md`](db/README.md).

### 2.2. Backend и API

Один общий REST API для всех клиентов.

**Аутентификация и авторизация:**
- Регистрация и вход по email и паролю.
- Пароли хранятся в хешированном виде (не открытым текстом).
- Токен (JWT или аналог) выдаётся при входе и передаётся в заголовке `Authorization: Bearer <token>`.
- Каждый пользователь видит и изменяет **только свои** задачи.

**Методы API — минимально необходимые:**

| Метод | Назначение |
|---|---|
| `POST /api/auth/register` | Регистрация |
| `POST /api/auth/login` | Вход, выдача токена |
| `GET /api/tasks` | Список задач текущего пользователя |
| `POST /api/tasks` | Создать задачу |
| `GET /api/tasks/{id}` | Получить задачу |
| `PUT /api/tasks/{id}` | Изменить задачу |
| `DELETE /api/tasks/{id}` | Удалить задачу |
| `PATCH /api/tasks/{id}/complete` | Отметить выполненной / снять отметку |
| `GET /api/tasks/summary` | Сводка: всего, выполнено, не выполнено, просрочено |

**Требования:**
- Все входные данные валидируются на сервере.
- Фильтры и поиск в списке задач: по статусу, по приоритету, поиск по тексту. Дополнительно — сортировка и постраничный вывод.
- Единый формат ответа для всех методов, например:
  ```json
  { "success": true, "data": { }, "message": "OK", "error_code": null }
  ```
- Корректные HTTP-коды: `400` (ошибка запроса), `401` (не авторизован), `403` (нет прав), `404` (не найдено), `500` (внутренняя ошибка).
- Основные операции логируются.

Спецификация: [`api/openapi.yaml`](api/openapi.yaml). Коллекция для проверки: [`postman/Professionals-Task.postman_collection.json`](postman/Professionals-Task.postman_collection.json).

### 2.3. Web-клиент

Сайт, работающий в браузере. Минимум **3–4 экрана**:

1. Регистрация / вход
2. Список задач (с фильтрами и поиском)
3. Создание и редактирование задачи
4. Сводка / аналитика по задачам

Требования:
- адаптивная вёрстка, корректная работа от **360 px** до **1920 px**;
- все списки — с пагинацией или бесконечной подгрузкой;
- пользовательские сообщения об ошибках понятны человеку;
- есть состояние «ничего не найдено» и состояние загрузки.

### 2.4. Desktop-клиент

Настольное приложение для Windows, Linux или macOS. **Не гибрид и не WebView** — это должна быть самостоятельная нативная программа, использующая тот же API.

Минимум **3–4 экрана** (например: вход, список задач, карточка задачи, сводка).

Допустимые технологии: C# / Avalonia, Python / PyQt, Electron (только если интерфейс нативный, без вставки web-страницы).

### 2.5. Mobile-клиент

Приложение на **React Native**. Минимум **3 экрана**:

1. Вход / регистрация
2. Список задач
3. Создание задачи

Требования:
- создание, редактирование, отметка выполнения и удаление задачи;
- авторизация с сохранением токена;
- приложение должно корректно работать на реальном устройстве или эмуляторе;
- снимки экранов положить в репозиторий (папка `screenshots/` или аналогичная).

## 3. Что сдавать

В вашем публичном репозитории на GitHub:

1. Исходный код базы данных, backend, web, desktop и mobile-клиентов.
2. Скрипт создания базы данных.
3. `README.md`: как запустить каждую часть, нужные переменные окружения, порты, версии ПО.
4. ER-диаграмма базы данных.
5. Документацию по API: README + спецификация (Swagger / OpenAPI).
6. Примеры запросов к API (curl, Postman или Swagger).
7. Скриншоты всех клиентов.

**Презентация не требуется.**
