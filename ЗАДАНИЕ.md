**Компетенция:** Программные решения для бизнеса
**Чемпионат:** «Профессионалы» 2027
**Формат:** работа в команде до 2 человек

> **Пошаговая инструкция — в [wiki репозитория](https://github.com/artemovsergey/professionals-task/wiki).**
> Задание разобрано по спринтам: 24 спринта, 54 страницы. Каждый шаг описан
> словами, подкреплён кодом, скриншотом и гифкой.

## 1. Описание

Нужно разработать систему учёта **технического обслуживания и ремонта (ТОиР)
промышленного оборудования** — «ТОиР-Проф».

Система ведёт полный цикл работы участка:

1. ведёт **график планового обслуживания** с периодичностью по видам работ;
2. принимает **заявки на ремонт** с автоматической нумерацией;
3. назначает **ремонтные бригады** и списывает **материалы и ЗИП**;
4. считает **простой оборудования** и **эффективность бригад**;
5. отдаёт **аналитику** руководителю в браузере и мастеру — в настольном клиенте.

Это полноценная бизнес-система: здесь проверяются не только умение собрать
«база → API → клиенты», но и проектирование (UML, нормализация), работа с
триггерами и хранимыми процедурами, тестирование и документация.

### Роли пользователей

| Роль | Кто это | Что видит |
|---|---|---|
| **Мастер** | начальник ремонтной бригады | заявки, график ТО, оборудование цеха, материалы |
| **Руководитель** | начальник участка | дашборд, аналитика, все реестры, сводные отчёты |
| **Администратор** | ИТ-специалист | пользователи, справочники, всё вышеперечисленное |

## 2. Стек

Стек **фиксированный** — это сделано для одинаковой проверки всех участников.

| Часть | Технология | Версия |
|---|---|---|
| База данных | PostgreSQL | 15+ |
| Backend / API | .NET (ASP.NET Core Web API) + Entity Framework Core | **.NET 10** |
| Desktop-клиент | C# / Avalonia (нативный UI, **без WebView**) | Avalonia 11 |
| Web-клиент | React + TypeScript + Vite | React 19 |
| Модульные тесты | xUnit + FluentAssertions | — |
| СУБД-инструменты | DBeaver или DataGrip | — |
| Тесты API | Postman | — |
| Диаграммы | Draw.io | — |

> **Мобильный клиент в задании отсутствует** и баллов за него не даёт.
> Упоминание «мобильный клиент для члена бригады» есть только во введении
> к сценарию — это часть легенды, а не отдельное задание.

> **Основная ОС на площадке — РедОС 8.0.** Отбор можно проходить на Windows,
> но код обязан собираться и запускаться на РедОС: никаких Windows-путей,
> `cmd` и PowerShell-команд. Инструкции по установке — на странице
> [01-Установка-инструментов](https://github.com/artemovsergey/professionals-task/wiki/01-Установка-инструментов).

## 3. Что должно работать

### 3.1. База данных

**Сущности:** пользователи и роли, цеха, оборудование, виды ТО, график
планового ТО, заявки на ремонт, ремонтные бригады и их состав, материалы и
ЗИП, списание материалов в заявки, журнал операций (аудит).

**Обязательные объекты:**

| Объект | Что делает |
|---|---|
| Ограничения уникальности | логин, инвентарный номер, номер заявки, артикул материала |
| Ограничения логической связанности | внешние ключи с осмысленными `ON DELETE` |
| Ограничения допустимых значений | пользовательские ENUM-типы: статус оборудования, статус заявки, приоритет |
| `CHECK` на хронологию | дата окончания не раньше даты начала |
| Триггер №1 | запрет смены статуса оборудования, выведенного из эксплуатации |
| Триггер №2 | комплексная проверка дат заявки при вставке и изменении |
| Функция №1 | расчёт простоя оборудования в часах |
| Функция №2 | расчёт следующей плановой даты обслуживания |
| Процедура №3 | сводный отчёт по цеху за период |

Скрипты `db/schema.sql`, `db/triggers.sql`, `db/functions.sql`, `db/seed.sql`
обязательны и должны выполняться подряд на чистой базе без ручных правок.

**Нормализация:** модель приводится к 3НФ, обоснование — в `db/README.md`.
ER-диаграмма обязательна.

### 3.2. Backend и API

Один общий REST API для обоих клиентов. **Стек: .NET 10, ASP.NET Core Web API,
Entity Framework Core.**

| Группа | Что реализовать |
|---|---|
| Аутентификация | регистрация, вход, JWT, три роли, изоляция данных по роли |
| Оборудование | CRUD, фильтры, поиск, пагинация |
| Справочник видов ТО | CRUD с запретом удаления используемой записи |
| График ТО | чтение, создание записи, отметка выполнения |
| Заявки | создание с автогенерацией номера `Z-YYYY-XXXX`, чтение, фильтры, назначение бригады, завершение |
| Бригады, материалы | CRUD, списание материалов в заявку с пересчётом стоимости |
| Аналитика | сводные KPI, срезы, простои, рейтинг эффективности бригад |
| Экспорт | отчёт в PDF + временная ссылка с тайм-аутом 15 секунд |

**Единый формат ответа — везде одинаковый:**

```json
{ "success": true,  "data": { }, "message": "OK",                    "error_code": null }
{ "success": false, "data": null,   "message": "Заявка не найдена",  "error_code": "NOT_FOUND" }
```

**HTTP-коды:** 200, 201, 400 (валидация), 401 (нет токена), 403 (нет прав),
404 (не найдено), 409 (конфликт состояния), 429 (слишком много запросов),
500 (внутренняя ошибка).

### 3.3. Desktop-клиент (Avalonia)

Нативное приложение, **без WebView**, работает **только через REST API**,
бизнес-логики на клиенте нет.

| Экран | Что на нём |
|---|---|
| Авторизация | вход, обработка ошибок |
| Дашборд мастера | показатели за смену |
| Оборудование цеха | реестр с фильтрами, поиском, сортировкой, пагинацией |
| График ТО | план работ на месяц |
| Заявки | жизненный цикл заявки, списание материалов |
| Материалы, бригады | справочники с остатками |
| Отчёты | сводка, выгрузка, офлайн-режим |

Общие требования: боковое меню, верхняя панель, хлебные крошки, всплывающие
уведомления, модальные окна ошибок, сортировка, пагинация, поиск, асинхронность
с индикатором, локальное логирование, автоблокировка при бездействии,
офлайн-кэш с автоотправкой изменений.

### 3.4. Web-клиент (React)

| Раздел | Что на нём |
|---|---|
| Дашборд руководителя | 6 KPI-карточек, круговая, столбчатая и линейная диаграммы, топ-5 простоев, таблица последних заявок, автообновление раз в 60 секунд |
| Аналитика | панель фильтров и 5 блоков: сводка по заявкам, анализ простоев, анализ материалов, выполнение графика ТО, эффективность бригад с рейтингом |
| Реестры | оборудование, заявки, график ТО, справочники, пользователи |
| Экспорт | PNG, CSV, PDF отдельными блоками и страницы целиком, печать |

Каналы обновления: WebSocket или SSE, fallback на опрос, автопереподключение
с экспоненциальной задержкой, индикатор статуса соединения.

Адаптивность: от 1024×768 до 1920×1080. Обработка ошибок 400, 403, 404, 409,
429, 500 с понятным сообщением.

### 3.5. Модульные тесты

Ровно **5 юнит-тестов** для desktop-клиента, AAA-структура, изоляция,
информативные имена:

| № | Тест | Что проверяет |
|---|---|---|
| 1 | `calculateDowntimeHours` | корректные даты; окончание раньше начала; `null` и некорректные значения |
| 2 | `validateWorkOrder` | все поля верны; нет обязательного поля; аварийная без причины; некорректные плановые даты |
| 3 | `calculateTotalMaterialCost` | несколько материалов; пустой список; количество = 0; отрицательные значения |

Эталон расчёта из задания: подшипник 6-205 — 4 шт × 850 = 3400; ремень
приводной — 2 шт × 1200 = 2400; масло И-20 — 10 л × 150 = 1500;
**итого 7300.00**.

### 3.6. Системный анализ и проектирование

Три UML-диаграммы в `docs/diagrams/`, каждая — исходник + PNG + SVG + README
с обоснованием:

1. **Use Case** — актёры, варианты использования, граница системы, связи `include` и `extend`;
2. **Activity** — процесс «Выполнение заявки на ремонт и ТО»: начало и конец, действия, ветвления, fork/join, дорожки;
3. **Class** — классы в три секции, связи, кратности.

### 3.7. Документирование и оформление

| Документ | Требование |
|---|---|
| Документация API | Swagger со всеми методами и моделями |
| Инструкция по развёртыванию | 8–10 страниц, пошагово |
| Руководство пользователя | для мастера и для руководителя |
| Презентация | 12–15 слайдов |
| Устное выступление | 5–7 минут плюс ответы на вопросы экспертов |

> **Ограничение по ИИ.** Использование ИИ **разрешено только для текстов
> документации и презентации**. Запрещено использовать ИИ для написания кода,
> SQL, триггеров, проектирования архитектуры БД и тестов.
