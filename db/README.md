# База данных системы «ТОиР-Проф»

PostgreSQL 15+. Четыре файла выполняются подряд, на чистой базе:

```bash
createdb -U toirprof toirprof
psql -h 127.0.0.1 -U toirprof -d toirprof -f db/schema.sql
psql -h 127.0.0.1 -U toirprof -d toirprof -f db/functions.sql
psql -h 127.0.0.1 -U toirprof -d toirprof -f db/triggers.sql
psql -h 127.0.0.1 -U toirprof -d toirprof -f db/seed.sql
psql -h 127.0.0.1 -U toirprof -d toirprof -f db/verify.sql
```

Первые четыре — развёртывание, пятый — самопроверка: он ничего не меняет
и печатает отчёт по каждому ограничению, триггеру и функции.

## ER-диаграмма

Исходник — `erd/er-diagram.drawio`, тот же рисунок в PNG — `erd/er-diagram.png`.
Открывается в Draw.io, diagrams.net и в приложении Draw.io на РедОС.

Главное, что видно на диаграмме и чего не видно в списке таблиц:

- **Одна заявка — одно оборудование.** Пресс ПР-2 не может быть причиной
  заявки на станок ТС-11: связь `work_orders.equipment_id` обязательна.
- **Заявка либо из графика, либо внеплановая.** Поле `schedule_id`
  nullable: если запись графика есть — заявка плановая, если NULL —
  аварийная или по обращению оператора.
- **Бригада назначается позже, чем создаётся заявка.** Поле `crew_id`
  nullable и заполняется при назначении; без бригады заявка остаётся
  в статусе «Черновик».
- **Списание ссылается и на заявку, и на материал.** Таблица
  `work_order_materials` — не просто список: в ней зафиксирована
  **цена на момент списания**, чтобы отчёт за прошлый год не изменился
  после переоценки склада.

## Нормализация

### Первая нормальная форма (1НФ)

Все значения атомарны. В частности:

- в `users` нет столбца «телефон, email» — это два разных пользователя
  в одной ячейке;
- в `work_orders` нет «материалы» списком — для этого есть отдельная
  таблица `work_order_materials`, одна строка на одну позицию;
- виды статусов и приоритетов — короткие строки с CHECK-ограничениями
  (`ck_equipment_status`, `ck_work_order_status`, `ck_work_order_priority`),
  а не произвольный текст: постороннее значение в столбец не запишется.

### Вторая нормальная форма (2НФ)

Каждая таблица имеет ключ, и все атрибуты зависят от всего ключа.

Связь «многие ко многим» вынесена в собственную таблицу:
`crew_members(crew_id, user_id)` — состав бригады. Если бы мы хранили
список участников в поле `crews.members`, одна бригада из трёх человек
занимала бы три почти одинаковые строки.

### Третья нормальная форма (3НФ)

Нет транзитивных зависимостей: между атрибутами, не входящими в ключ,
зависимостей нет.

| Что было бы нарушением | Как сделано правильно |
|---|---|
| `equipment.workshop_name` | `equipment.workshop_id → workshops.name` |
| `work_orders.status_name` | `status` — одно из значений CHECK, имя не хранится отдельно |
| `materials.price * quantity` | `cost` — вычисляемое поле в `work_order_materials` |
| `work_orders.equipment_name` | `work_orders.equipment_id → equipment.name` |

Название цеха, оборудования и материала хранится **только один раз** —
в справочнике. Заявка на пресс ПР-2 не хранит строку «Гидравлический
пресс ПР-2»: она хранит идентификатор. Переименовали пресс — обновили
одну строку `equipment`, а не двести строк истории заявок.

## Ограничения целостности

### UNIQUE — 4 обязательных

| Ограничение | Что защищает |
|---|---|
| `uq_users_username` | Два пользователя с одинаковым логином |
| `uq_equipment_inventory_number` | Две единицы с одним инвентарным номером |
| `uq_work_orders_number` | Заявки с одинаковым номером `Z-YYYY-XXXX` |
| `uq_materials_sku` | Один артикул на два наименования |

Плюс служебные: `uq_crew_members_crew_user` (один человек не может
состоять в одной бригаде дважды), `uq_maintenance_schedule_slot`
(одно и то же ТО не планируется на одну дату дважды).

### CHECK — хронология и допустимые значения

| Ограничение | Правило |
|---|---|
| `ck_equipment_commission_date` | Дата ввода в эксплуатацию обязательна |
| `ck_equipment_decommission_date` | Дата снятия не раньше даты ввода |
| `ck_equipment_criticality` | Влиятельность от 1 до 5 |
| `ck_work_order_planned_dates` | Дата окончания не раньше даты начала |
| `ck_work_order_actual_dates` | Фактическое окончание не раньше фактического начала |
| `ck_work_order_downtime` | Простой неотрицателен |
| `ck_work_order_number_format` | Номер заявки по маске `^Z-[0-9]{4}-[0-9]{4}$` |
| `ck_maintenance_schedule_dates` | У записи со статусом «Выполнено» обязана быть дата выполнения |

Проверка `CURRENT_DATE` внутри CHECK запрещена: PostgreSQL требует от
выражений в CHECK неизменяемости (IMMUTABLE). Поэтому «не раньше
сегодняшнего дня» в БД не проверяется — это делает приложение,
а хронология внутри одной строки проверяется базой.

### Наборы значений — 3 CHECK-ограничения

| Ограничение | Столбец | Значения |
|---|---|---|
| `ck_equipment_status` | `equipment.status` | В работе · В ремонте · В простое · Выведено из эксплуатации |
| `ck_work_order_status` | `work_orders.status` | Создана · Назначена · В работе · Ожидает материалов · Выполнена · Закрыта · Отменена |
| `ck_work_order_priority` | `work_orders.priority` | Низкий · Средний · Высокий · Критический |

Русские значения — не опечатка. Приложение, база и эксперт видят одни
и те же строки в журнале, отчёте и на экране.

Отдельный тип `CREATE TYPE … AS ENUM` здесь не используется намеренно:
драйвер Npgsql отправляет строку параметром типа `text`, и PostgreSQL
отвергает запись в enum-колонку с ошибкой `42804` («колонка priority
имеет тип work_order_priority, а выражение — text»). Ограничение CHECK
даёт ту же защиту от посторонних значений, но принимает обычную строку.

### Каскадные действия

| Связь | Правило | Почему |
|---|---|---|
| `maintenance_schedule.equipment_id` | **CASCADE** | График — часть жизни единицы; вместе с ней удаляется и график |
| `crew_members.crew_id` / `user_id` | **CASCADE** | Участник бригады без бригады — бессмысленная строка |
| `work_orders.equipment_id` | **RESTRICT** | Нельзя удалить пресс, на который есть заявки: история ремонта не должна исчезать |
| `work_orders.crew_id`, `assigned_to` | **SET NULL** | Бригаду можно закрыть, заявка должна остаться |
| `operation_log.user_id` | **SET NULL** | Историю нельзя терять при увольнении |
| `maintenance_types`, `materials` | **RESTRICT** | Справочник в отчётах прошлых лет не переписывается |

## Триггеры

| Триггер | Момент | Что делает |
|---|---|---|
| `trg_equipment_status_guard` | BEFORE UPDATE на `equipment` | Запрещает менять статус, если единица уже выведена из эксплуатации |
| `trg_work_order_dates_check` | BEFORE INSERT/UPDATE на `work_orders` | Комплексная проверка четырёх пар дат и пересчёт простоя |
| `trg_audit_work_orders` | AFTER INSERT/UPDATE/DELETE на `work_orders` | Пишет историю в `operation_log` |
| `trg_audit_equipment` | AFTER INSERT/UPDATE/DELETE на `equipment` | То же для оборудования |

Триггер проверки дат нельзя заменить на `CHECK`: правило «завершённая
заявка обязана иметь фактические даты и причину» зависит от **статуса**,
а `CHECK` в PostgreSQL не может ссылаться на другие столбцы таблицы.

## Функции и процедура

```sql
SELECT fn_calculate_downtime(TIMESTAMPTZ '2026-03-20 08:00', TIMESTAMPTZ '2026-03-20 20:30');
-- 12.50

SELECT fn_next_maintenance_date(DATE '2026-01-10', 90);
-- 2026-04-01  (первый день месяца, следующего после +90 дней)

CALL proc_workshop_report('aaaaaaaa-0000-0000-0000-000000000002',
                          DATE '2026-03-01', DATE '2026-03-31');
```

Процедура работает через `RAISE NOTICE` — её вывод виден в psql,
DBeaver и в логе приложения. Для API добавлено представление
`v_workshop_report`: вызвать процедуру из C# нельзя, а читать
представление — обычный `SELECT`.

## Как проверить

```bash
psql -h 127.0.0.1 -U toirprof -d toirprof -f db/verify.sql
```

Скрипт печатает отчёт по разделам: состав данных, показатели дашборда,
ограничения, триггеры, функции, процедура, списание. В конце — строка
`ИТОГО` и список непрошедших проверок. Если список пуст, схема работает.
