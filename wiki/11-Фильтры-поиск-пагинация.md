# Что делаем на этой странице

Список задач — самый нагруженный маршрут приложения. Им пользуются все три
клиента, и он должен уметь три вещи: сузить выборку, отсортировать и отдать
по страницам. Всё это делается на сервере: клиент не должен забирать все
задачи и фильтровать их у себя.

Подготовка: получим токен и положим его в файл, чтобы дальше команды были
короткими.

```bash
curl -s -X POST http://localhost:5000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"ivanov@college.ru","password":"Password123"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["token"])' > /tmp/token
```

![[images/api11-s0-token.png]]
*Токен сохранён в `/tmp/token` — дальше используем `T=$(cat /tmp/token)`*

# Шаг 1. Список без фильтров

```bash
bash q.sh 'pageSize=3'
```

где `q.sh` — короткая обёртка:

```bash
API=http://localhost:5000
T=$(cat /tmp/token)
code=$(curl -s -o /tmp/r.json -w '%{http_code}' "$API/api/tasks?$1" -H "Authorization: Bearer $T")
echo "GET /api/tasks?$1  ->  HTTP $code"
python3 -m json.tool --no-ensure-ascii /tmp/r.json
```

![[images/api11-s1-default.png]]
*`total` — сколько всего задач, `items` — только текущая страница*

Ключевая идея пагинации: `total` и `items` отвечают на разные вопросы.
`total` нужен для кнопок страниц, `items` — для отрисовки. Если отдавать
только `items`, клиент не сможет показать «стр. 2 из 5».

# Шаг 2. Фильтр по статусу

```bash
bash q.sh 'status=done&pageSize=3'
```

![[images/api11-s2-filter-status.png]]
*`total: 1` — выполненная задача у пользователя одна*

Обратите внимание: фильтр меняет и `items`, и `total`. Считать `total` нужно
**после** применения фильтров, иначе пагинация покажет чужие цифры.

# Шаг 3. Фильтр по приоритету

```bash
bash q.sh 'priority=high&pageSize=3'
```

![[images/api11-s3-filter-priority.png]]
*Только задачи с высоким приоритетом*

Фильтры складываются, а не заменяют друг друга: `status=done&priority=high`
даст задачи, которые одновременно выполнены и важны.

# Шаг 4. Поиск по названию

```bash
bash q.sh 'q=%D0%B7%D0%B0%D0%B4&pageSize=3'
```

![[images/api11-s4-search.png]]
*Найдены задачи, в названии которых есть «зад»*

Строку поиска нужно кодировать: кириллица в адресе передаётся как
percent-encoding. В браузере это делает `URLSearchParams` сам, в `curl` —
`--data-urlencode` или готовый код вида `%D0%B7`.

# Шаг 5. Сортировка по сроку

```bash
bash q.sh 'sort=dueDate&order=asc&pageSize=3'
```

![[images/api11-s5-sort-due.png]]
*Сначала задачи без срока, затем по возрастанию даты*

Пустые даты сортируются первыми — это особенность PostgreSQL: `NULL` меньше
любой даты. Если такое поведение не устраивает, добавьте
`ORDER BY due_date NULLS LAST`.

# Шаг 6. Вторая страница

```bash
bash q.sh 'page=2&pageSize=3'
```

![[images/api11-s6-page-2.png]]
*Другая тройка задач: `page: 2`, `total` не изменился*

Пагинация — это смещение, а не курсор:

```csharp
var items = await query
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .ToListAsync();
```

Смещение работает быстро на десятках тысяч строк. Если задач станет больше,
переходите на курсорную пагинацию — но на этом объёме она не нужна.

# Шаг 7. Границы параметров

```bash
bash q.sh 'pageSize=999'
```

![[images/api11-s7-bad-pagesize.png]]
*`400` и `VALIDATION_ERROR`: сервер не отдаст тысячу задач одним запросом*

Параметры проверяются **до** обращения к базе:

```csharp
if (page < 1) return Api.Fail(400, "page должен быть не меньше 1", "VALIDATION_ERROR");
if (pageSize is < 1 or > 100) return Api.Fail(400, "pageSize от 1 до 100", "VALIDATION_ERROR");
```

Без верхней границы один запрос с `pageSize=1000000` положит и сервис, и
базу. Это самая частая находка проверяющих.

# Шаг 8. Сборка запроса целиком

```csharp
var userId = Api.CurrentUserId(user);
var query = db.Tasks.Where(t => t.UserId == userId);

if (!string.IsNullOrWhiteSpace(status))   query = query.Where(t => t.Status == status);
if (!string.IsNullOrWhiteSpace(priority)) query = query.Where(t => t.Priority == priority);
if (DateOnly.TryParse(dueDate, out var due)) query = query.Where(t => t.DueDate == due);
if (!string.IsNullOrWhiteSpace(q))        query = query.Where(t => t.Title.Contains(q));

var total = await query.CountAsync();
```

Порядок строк важен:

1. **сначала** ограничение по владельцу — иначе можно подсчитать чужие задачи;
2. **затем** фильтры, каждый добавляет условие в тот же `IQueryable`;
3. **после** всех условий считается `total` — уже по отфильтрованной выборке.

![[images/api11-s9-code-filters.png]]
*Условия добавляются по одному, лишние не меняют запрос*

# Шаг 9. Сортировка

```csharp
query = (sort, order) switch
{
    ("dueDate", "asc")  => query.OrderBy(t => t.DueDate),
    ("dueDate", _)      => query.OrderByDescending(t => t.DueDate),
    ("priority", "asc") => query.OrderBy(t => t.Priority),
    ("priority", _)     => query.OrderByDescending(t => t.Priority),
    ("title", "asc")    => query.OrderBy(t => t.Title),
    ("title", _)        => query.OrderByDescending(t => t.Title),
    (_, "asc")          => query.OrderBy(t => t.CreatedAt),
    _                   => query.OrderByDescending(t => t.CreatedAt),
};
```

Значения `sort` и `order` приходят от клиента, поэтому ветка по умолчанию
обязана существовать: неизвестный `sort` не должен ронять сервис. Здесь он
превращается в сортировку по дате создания.

![[images/api11-s10-code-sort.png]]
*Каждая пара «поле + направление» — отдельная ветка, последняя ветка — защита*

# Шаг 10. Клиент собирает строку запроса

```javascript
listTasks: (params = {}) => {
  const query = new URLSearchParams();
  for (const [key, value] of Object.entries(params)) {
    if (value !== '' && value !== null && value !== undefined) query.set(key, value);
  }
  const qs = query.toString();
  return request('GET', `/api/tasks${qs ? `?${qs}` : ''}`);
},
```

Пустые значения не попадают в строку: иначе адрес станет
`/api/tasks?status=&pageSize=20`, и сервер придётся разбирать, что имелось в
виду. `URLSearchParams` заодно кодирует кириллицу — пункт 4 можно не
дублировать руками.

![[images/api11-s11-client-params.png]]
*Клиент отбрасывает пустые параметры и кодирует остальные*

# Проверка

| Проверка | Ожидание |
|---|---|
| без параметров | весь список, `pageSize: 20` по умолчанию |
| `status=done` | `items` и `total` — только выполненные |
| `status=done&priority=high` | оба условия применяются вместе |
| `q= зад` в названии | поиск работает, регистр не важен |
| `sort=dueDate&order=asc` | сроки по возрастанию |
| `page=2&pageSize=3` | вторая тройка, `page: 2` |
| `pageSize=999` | `400`, `VALIDATION_ERROR` |
| `page=0` | `400`, `VALIDATION_ERROR` |
| фильтр с чужим `id` в URL | фильтр не применяется, данные те же |

# Если что-то не получилось

| Симптом | Что делать |
|---|---|
| `total` не меняется при фильтре | `CountAsync()` вызывается до добавления условий |
| Фильтр молча игнорируется | сравнение строк регистрозависимо, а в базе значение с другой регистровой формой |
| Возвращаются чужие задачи | потерян `Where(t => t.UserId == userId)` — самая частая и самая дорогая ошибка |
| `page=2` возвращает ту же страницу | забыли `Skip((page - 1) * pageSize)` |
| Кириллица в `q` не ищется | не percent-encoded: в браузере за это отвечает `URLSearchParams` |
| `ORDER BY` не применяется | `OrderBy` вызван после `ToList()` — запрос уже выполнен |
| Сервис падает на `sort=unknown` | нет ветки по умолчанию в `switch` |
| Страница отдаётся целиком | не проверяется верхняя граница `pageSize` |
