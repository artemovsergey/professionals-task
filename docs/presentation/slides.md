## Слайд 2. Проблема и цель

**Проблема**

- Учёт ТОиР ведётся в таблицах: график плановых работ, заявки на ремонт, склад ЗИП — отдельно друг от друга
- Невозможно посчитать простой оборудования и долю аварийных заявок
- Не видно, какая бригада чаще задерживает работы

**Цель**

- Единая база данных с ограничениями, которые не дают внести неправильные данные
- Один REST API для двух клиентов
- Аналитика: простои, эффективность бригад, выполнение графика ТО

> На экране: две колонки «проблема / цель».

## Слайд 3. Ключевые роли и сценарий работы

| Роль | Что делает |
|------|------------|
| Мастер участка | Заводит заявку, назначает бригаду, отмечает выполнение, списывает материалы |
| Руководитель цеха | Смотрит сводку и аналитику, контролирует простои и рейтинг бригад |
| Администратор | Ведёт справочники: оборудование, виды ТО, бригады, материалы, пользователи |

**Цикл работы**

```
График ТО → заявка на ремонт → назначение бригады → выполнение и списание → аналитика
```

> На экране: таблица ролей и схема цикла.

## Слайд 4. Архитектура решения

```
Desktop Avalonia        Web React        Postman · Swagger
   мастер участка    руководитель цеха   проверка контракта
              │            │                   │
              └──────── HTTPS, Bearer JWT ─────┘
                              ▼
            API · ASP.NET Core .NET 10
      сервисы → EF Core → Npgsql, обёртка {success, data, …}
                              ▼
          PostgreSQL 15+ — 13 таблиц, 3 типа, 4 триггера
```

- Логика проверок живёт в базе, а не в клиентах: иначе Desktop и Web посчитали бы по-разному
- Клиенты только показывают и отправляют — бизнес-правил на клиенте нет

> На экране: схема, показать путь запроса от клиента к базе.
> В `slides.html` схема набрана настоящими блоками, а не псевдографикой:
> в презентации псевдографика ломается о шрифт и обрезается по краю слайда.

## Слайд 5. Модель данных

**13 таблиц**

- Справочники: `roles`, `workshops`, `maintenance_types`, `crews`, `materials`
- Учёт: `users`, `equipment`, `maintenance_schedule`, `work_orders`
- Связи и служебные: `crew_members`, `work_order_materials`, `operation_log`, `work_order_counters`

**Нормализация**

- 1НФ — списки вынесены в отдельные таблицы, перечисления заменены типами
- 2НФ — связь «сотрудник ↔ бригада» вынесена в `crew_members`
- 3НФ — название цеха, стоимость и статус не дублируются; `cost` считает база

> На экране: `docs/diagrams/class-model.png` (диаграмма классов).

## Слайд 6. Ограничения целостности

| Вид ограничения | Пример |
|-----------------|--------|
| `UNIQUE` | логин, инвентарный номер, артикул, номер заявки |
| `CHECK` | хронология дат, критичность 1…5, формат номера `Z-YYYY-XXXX` |
| Перечисления | статусы оборудования, заявки и приоритет заданы типами `ENUM` |
| `ON DELETE` | график удаляется каскадом, справочники защищены `RESTRICT` |
| Вычисляемые поля | `cost` = количество × цена, простой считает функция |

**Правило:** ошибка из базы доходит до клиента как понятный текст с кодом,
а не как «500 Internal Server Error».

> На экране: окно DBeaver со вкладкой «Ограничения» на таблице `equipment`.

## Слайд 7. Триггеры, функции и процедура

- **Триггер 1.** Статус оборудования, выведенного из эксплуатации, изменить нельзя
- **Триггер 2.** Проверка дат заявки и пересчёт простоя при каждой записи
- **Триггеры 3 и 4.** Журнал операций: кто и что изменил
- **Функция 1.** `fn_calculate_downtime` — простой в часах между двумя метками времени
- **Функция 2.** `fn_next_maintenance_date` — следующая плановая дата по периодичности
- **Процедура.** `proc_workshop_report` — сводный отчёт по цеху за период

> На экране: вывод `db/verify.sql`, где каждая проверка даёт строку «ОК».

## Слайд 8. REST API

**Единый формат ответа**

```json
{
  "success": true,
  "data": { "...": "..." },
  "message": "OK",
  "error_code": null
}
```

**Коды ответов**

`200` · `201` · `400` (ошибка данных) · `401` (нет токена) · `403` (нет прав) ·
`404` (не найдено) · `409` (конфликт) · `429` (слишком часто) · `500` (внутренняя ошибка)

**Примеры сценариев ошибок**

| Код | Когда |
|-----|-------|
| `STATUS_LOCKED` | попытка вернуть в работу выведенное оборудование |
| `CREW_BUSY` | бригада уже ведёт другую заявку «В работе» |
| `NOT_ENOUGH_STOCK` | на складе меньше, чем пытаются списать |

> На экране: Swagger UI с нажатой кнопкой «Authorize».

## Слайд 9. Desktop-клиент

**Мастер работает в восьми окнах:** авторизация, дашборд, оборудование, график ТО,
заявки, бригады, материалы, отчёты.

- Нативный интерфейс на Avalonia — без встраивания веб-страниц
- Индикатор связи, всплывающие сообщения, модальные окна ошибок
- **Работа без сети:** последние загруженные данные и очередь отложенных операций,
  которая уходит на сервер сама, как только связь вернётся
- Локальный журнал: `%LOCALAPPDATA%/ToirProf/logs/client.log`

> На экране: окно «Заявки» с выбранной заявкой и историей изменений.

## Слайд 10. Web-клиент: сводка и обновления

**Дашборд руководителя**

- Шесть KPI-карточек: заявки, средний простой, доля аварийных, выполнение плана ТО, списание, цехи
- Круговая, столбчатая и линейная диаграммы, топ-5 единиц по простою, последние заявки
- **Обновление в реальном времени:** Server-Sent Events, а если поток недоступен —
  резервный опрос раз в минуту с переподключением

**Индикатор в шапке**

| Значок | Значение |
|--------|----------|
| `SSE` | данные приходят потоком |
| `Опрос` | поток недоступен, данные забираются раз в 60 секунд |
| `Нет связи` | сервер недоступен, показаны последние загруженные данные |

> На экране: дашборд с индикатором `SSE`.

## Слайд 11. Аналитика и экспорт

**Пять блоков аналитики**

1. Сводка по заявкам
2. Анализ простоев — топ единиц оборудования
3. Расход материалов
4. Выполнение графика ТО
5. Эффективность бригад с рейтингом

**Выгрузка:** каждый блок в CSV, PNG и PDF; вся страница печатается.
На сервере — отчёт в PDF по временной ссылке, которая живёт 15 секунд.

**Фильтры:** период, цех. Данные одного блока и общих KPI берутся одним запросом,
поэтому цифры в разных блоках не расходятся.

> На экране: раздел «Аналитика», раскрытые блоки и меню экспорта.

## Слайд 12. Тестирование

**Пять юнит-тестов для настольного клиента** (требование задания)

| Тест | Что проверяет |
|------|---------------|
| `calculateDowntimeHours` | корректные даты, окончание раньше начала, пустые значения |
| `validateWorkOrder` | все поля заполнены, нет обязательного, аварийная без причины, неверные плановые даты |
| `calculateTotalMaterialCost` | несколько материалов, пустой список, нулевое и отрицательное количество |

- Эталон из задания: 4 × 850 + 2 × 1200 + 10 × 150 = **7 300,00**
- Все 13 проверок проходят; логика вынесена отдельно от интерфейса, поэтому тесты не требуют окна и базы

**Проверка ограничений базы** — скрипт `db/verify.sql`: каждое ограничение,
триггер и функция проверяются отдельной строкой с ожидаемым результатом.

> На экране: вывод `dotnet test` и отчёт `db/verify.sql`.
