# План wiki: система «ТОиР-Проф»

Внутренний документ организатора. Страницы wiki генерируются по этому плану,
как и раньше, но теперь под задание чемпионата 2027 года.

## Зачем

Студенту не дают задание «разберись сам». Мы **сами выполняем задание** и
расписываем решение по шагам, с готовым кодом, скриншотами и гифками.

Ключевое отличие от прошлой версии wiki: **разбивка не по сессиям чемпионата,
а по спринтам задания**. Расписание чемпионата (3 дня, 5 сессий) меняется от
этапа к этапу, а состав работы — нет. Спринт = законченный кусок системы,
который можно проверить: запустить, посмотреть, закрыть критерий оценивания.

## Формат страницы (обязательный)

```
- одна страница = один спринт в пределах 2–3 часов, номер страницы сквозной 01…54
- первая строка: спринт, название и сколько минут займёт страница
- тайминг: блоки по 10–30 минут, каждый блок — заголовком «## Шаг N. …»
- инструкции императивом, на «вы»: «создайте», «проверьте», «запустите»
- готовый код целиком, с указанием пути файла над блоком
- команды терминала — в блоках ```bash, с пояснением, что делает команда
- > **Замечание** — важные тонкости, ловушки, частые ошибки
- блок «Если что-то не получилось» — таблица «Симптом | Что делать»
- блок «Проверка» — одна команда, которая доказывает, что страница сделана
- блок «Коммит» — сообщение коммита в конце страницы
- навигация: предыдущая страница · [все спринты](Home) · следующая страница
- без воды; язык — русский, технические термины и код — как есть
```

## Правила медиа

Каждый шаг, где есть что показать, подкрепляется иллюстрацией:

| Вид | Куда | Как подключить |
|---|---|---|
| Скриншот | `wiki/images/NN-<slug>.png` | `![подпись](images/NN-<slug>.png)` + курсивная подпись |
| Гифка | `wiki/gifs/NN-<slug>.gif` | `![подпись](gifs/NN-<slug>.gif)` + курсивная подпись |

`NN` — двузначный номер страницы, `slug` — латиницей в kebab-case. Один и тот
же `slug` можно использовать и для PNG, и для GIF: это разные каталоги.

Ссылки на изображения — **стандартным markdown**, не Obsidian-викилинками:
такой синтаксис одинаково работает в Obsidian, в GitHub Wiki и в Gogs.

## Как всё устроено технически

| Файл | Зачем |
|---|---|
| `tools/wiki/sprints.py` | **единственный источник правды**: 25 спринтов и 54 страницы |
| `tools/wiki/gen_pages.py` | рендерер: страницы, `Home.md`, `_Sidebar.md`, чек-лист захвата |
| `tools/capture/rec.py` | захват экрана в PNG и GIF |
| `tools/capture/make-gifs.py` | сборка GIF из готовых PNG |
| `tools/capture/run-page.sh` | выполнить команду шага и снять результат |
| `docs/capture-checklist.md` | что и под каким именем снимать (генерируется) |
| `tools/publish-wiki.sh` | публикация `wiki/` в GitHub Wiki |

Правило простое: **правьте `sprints.py`, а не готовые страницы**. Страницы
перезаписываются генератором, ручные правки в `wiki/*.md` будут потеряны.

```bash
# пересобрать вики после правки sprints.py
python3 tools/wiki/gen_pages.py

# только проверить, ничего не записывая
python3 tools/wiki/gen_pages.py --check
```

Проверка валидирует: 54 страницы, сплошную нумерацию, уникальность имён
файлов, отсутствие битых относительных ссылок и дублей имён медиа.

## Контракт API (общий для обоих клиентов, не отклоняться)

Базовый адрес при разработке: `http://localhost:5080`

Обёртка ответа — **везде одинаковая**:

```json
{ "success": true,  "data": { }, "message": "OK",                   "error_code": null }
{ "success": false, "data": null,   "message": "Заявка не найдена",  "error_code": "NOT_FOUND" }
```

| Метод | Путь | Коды |
|---|---|---|
| POST | `/api/auth/register` | 201, 400, 409, 500 |
| POST | `/api/auth/login` | 200, 401, 500 |
| GET | `/api/equipment` | 200, 401, 500 |
| POST | `/api/equipment` | 201, 400, 409, 500 |
| GET | `/api/maintenance-types` | 200, 401, 500 |
| GET | `/api/maintenance-schedule` | 200, 401, 500 |
| POST | `/api/work-orders` | 201, 400, 401, 500 |
| POST | `/api/work-orders/{id}/crew` | 200, 400, 401, 403, 404, 409, 500 |
| POST | `/api/work-orders/{id}/complete` | 200, 400, 401, 404, 409, 500 |
| GET | `/api/dashboard/summary` | 200, 401, 500 |
| GET | `/api/dashboard/events` (SSE) | 200, 401, 500 |
| GET | `/api/analytics/downtime` | 200, 401, 500 |
| GET | `/api/analytics/crews` | 200, 401, 500 |
| POST | `/api/reports` | 201, 400, 401, 500 |
| GET | `/api/reports/download/{token}` | 200, 401, 404 |

**Номер заявки** формируется автоматически в формате `Z-YYYY-XXXX`
(`Z-2026-0048`) и не редактируется пользователем.

**Коды ошибок** в `error_code`: `NOT_FOUND`, `INVALID_TOKEN`,
`STATUS_LOCKED`, `CREW_BUSY`, `NOT_ENOUGH_STOCK`, `VALIDATION_ERROR`.

Токен: `Authorization: Bearer <token>`. Секрет JWT и строка подключения —
**только через переменные окружения**, файл `.env` — в `.gitignore`.

## Ограничения по окружению

- **Основная ОС на площадке — РедОС 8.0.** Инструкции даются и для Windows,
  и для РедОС. Запрещено: Windows-пути, `\` в путях, PowerShell-команды,
  `cmd`, `C:\`.
- На РедОС нет Docker в оснащении площадки → **PostgreSQL ставится нативно**
  через `dnf`, не через контейнер.
- Инфраструктурный лист: РедОС 8.0, .NET 10 + Avalonia, Node.js 22,
  Python 3.11, DBeaver, Postman, Draw.io, Rider или WebStorm.
- Студент тренируется на Windows, но обязан проверить, что проект
  собирается и запускается на РедОС.

## Что проверяется на этапах

Критерий оценивания разложен на четыре группы:

| Группа | Что входит |
|---|---|
| **А. Проектирование** | use case, activity, class, проектирование и реализация БД |
| **Б. Разработка** | ограничения целостности БД, API, desktop-клиент, web-клиент |
| **В. Тестирование** | модульные тесты desktop-клиента |
| **Г. Документирование и оформление** | культура безопасного труда, профессиональная культура, документация API, инструкция, руководство, презентация и выступление |

Отсюда порядок спринтов: **проектирование идёт первым** (классы из Class
диаграммы становятся контрактом для БД и API), база данных разбита на три
спринта по группам критериев, desktop и web — по четыре спринта каждый.

Две группы критериев — культура безопасного труда и профессиональная культура —
не требуют артефактов в репозитории. Это 10 баллов, которые набираются
поведением на площадке: соблюдать правила техники безопасности и показывать
работу экспертам.
