Дата: 2026-10-08
Статус: утверждён
Предмет: тренировочный курс по конкурсному заданию «Программные решения для бизнеса», Региональный этап чемпионата по профессиональному мастерству «Профессионалы» 2027.

## 1. Назначение

У пользователя уже есть мануал, сделанный на простом учебном задании todo
(репозиторий `professionals-task`, GitHub Wiki, 28 страниц). Требуется такой же
по формату и требованиям мануал — пошаговая инструкция со скриншотами и gif —
но построенный на **реальном** конкурсном задании 2027 года и покрывающий **все
100 баллов**.

Мануал — это **тренировочный курс до чемпионата**, а не шпаргалка. На стартовой
странице это проговаривается прямым текстом: на соревнованиях курс закрыт,
чистый лист.

автоблокировка при бездействии 15 с, пагинация 25/50/100, 4 KPI-карточки на
Desktop и 6 на Web, экспоненциальное переподключение 1/2/5/10 с, ссылка на
отчёт с таймаутом 15 секунд и 403 после.

## 6. Структура курса

24 занятия по 2,5 ч, 60 ч всего. Основная линия — занятия 1–23 (57,5 ч);
занятие 24 не укладывается в один подход и используется как блок адресной
отработки. На чемпионате 15 ч, тренировка вчетверо длиннее: это оправдано,
потому что 163 аспекта проверяют мелочи.

Порядок курса не совпадает с порядком на чемпионате намеренно: база и
проектирование тянут за собой всё остальное, а документацию и презентацию
проще писать, когда система работает.

Нумерация субкритериев в исходном файле сбита: после «Б1 Ограничения
целостности» идут два отдельных блока «Разработка API», затем Desktop, затем
Web. Поэтому в колонке «Контур» стоят названия, а не номера.

страница → балл». Она позволяет тренироваться по слабым местам, а не подряд,
и служит главным инструментом тренера.

## 7. Шаблон страницы

Базовый — как в `professionals-task`, плюс три новых блока.

```
# NN. Название занятия
Сессия N. <контур> · <NN>–<NN> мин
**Балл:** 0.5 · **Аспект:** «Уникальность номера заявки»

## Как читать эту страницу
## Перед началом            (> **Замечание:** …)
## Шаг 1. … … ## Шаг N. …  (код → пояснение → !![](images/…) *подпись*)
## Проверка                 (команда + ожидаемый результат)
## Коммит                   (git add … / git commit -m "…")
## На РедОС 8.0 отличается
## Если что-то не получилось  (таблица «Симптом | Что делать»)
---
Дальше: [NN-Название](NN-…)
```

Правила:

- GIF ставится только там, где статичный скриншот не учит: вход в систему,
  round-trip создания заявки, приход real-time события, offline → синхронизация,
  генерация отчёта, мобильный ввод. Остальное — обычные PNG.
- Каждая команда даётся в двух вариантах: строка для Windows и строка для
  РедОС 8.0.
- Блок «На РедОС 8.0 отличается» содержит только реальные отличия: пути,
  `dnf` вместо `winget`, отсутствие PowerShell, `git config --global
  core.autocrlf input`.
- Тон разговорный, как в отборном мануале: «Не застревайте», «Это снимает
  баллы», «Одна команда вместо четырёх».
- Имена файлов: `images/desk18-s3-workorder-timeline.png`,
  `images/web21-gif-dashboard-live.gif`.

Чтобы страницы не устаревали при ежегодном изменении задания на 30 %, текст
шагов формулируется независимо от номеров критериев: меняются таблица на
`Home.md` и номера критериев в шапках, сам текст остаётся валидным.

## 8. Производство скриншотов и gif

Всё снимается с работающего эталона автоматически, скриптами в `tools/`.

| Что снимаем | Как | Чем |
|---|---|---|
| БД, триггеры, функции | окно CloudBeaver в браузере | Playwright |
| Web-клиент | скриншот в нужной точке сценария | Playwright |
| Web gif | запись сценария → mp4 → gif | playwright video + ffmpeg |
| Desktop | захват окна по PID | Python `PrintWindow` → PNG |
| Desktop gif | покадровый захват в цикле | Pillow `save(save_all=True)` |
| Мобильный | эмулятор Pixel 7 API 35 | `adb exec-out screencap` |
| Мобильный gif | запись экрана | `adb shell screenrecord` + ffmpeg |
| Диаграммы UML, ERD | PlantUML jar | `plantuml -tpng` |

Объём: ~180 скриншотов и ~30 gif. Съёмка идёт пачками по занятию: запустил
сценарий → скрипт отсёк кадры → подписал в markdown.

Проверено на машине: PostgreSQL 16 (служба `postgresql-x64-16` работает),
Playwright chromium-1228, `ffmpeg-win64.exe` в `%LOCALAPPDATA%\ms-playwright\ffmpeg-1011\`,
Pillow 12.3, Java 11, Android SDK с AVD Pixel_5_API_33 и Pixel_7_API_35,
dotnet, node 24. Не хватает: `psql` в PATH, docker, plantuml (ставится из
Maven Central), draw.io.

## 9. Скрипт судьи

Колонка «Методика проверки аспекта» содержит готовые автотесты: «Выполняется
INSERT двух записей с одинаковым инвентарным номером», «Запрос GET /equipment
с параметрами workshop_id, status, search», «Скачивание файла на 5-й секунде
и повторное обращение на 20-й», «POST /work-orders/{id}/complete со списком
израсходованных материалов».

Собирается `tools/judge/` — скрипт, проходящий по всем 163 аспектам и
печатающий отчёт вида `закрыто 87.5 из 100`.

Две роли:

- для сборки эталона — способ не пропустить критерий;
- для ученика — превращает мануал из чтения в тренажёр с обратной связью.

## 10. Порядок работ

Вики пишется **параллельно** с эталоном, а не после: иначе получится три
месяца кода и потом месяц текста, и ученик получит мануал на выходе.

| Фаза | Содержание | Срок |
|---|---|---|
| 0. Инструменты | репозитории, PlantUML, ffmpeg, скрипты съёмки. Контрольная проверка: снят 1 скриншот и 1 gif с каждого из трёх клиентов | 1 день |
| 1. Данные и API | схема БД, триггеры, функции, процедура, тестовые данные, 4 микросервиса, Gateway | ~2 недели |
| 2. Web-клиент | 40 аспектов, 20.4 балла | ~3 недели |
| 3. Desktop | 44 аспекта, 17.4 балла | ~2,5 недели |
| 4. Мобильный + тесты | заготовка Android, 20 аспектов unit-тестов | ~1 неделя |
| 5. Документация | API, развертывание, руководство, презентация, репетиция выступления | ~1 неделя |

Каждая фаза заканчивается прогоном съёмки по закрытым критериям и коммитом
страниц в wiki.

Оценка объёма: 100–120 часов работы. Работы делятся по фазам так, чтобы после
любой фазы оставался самостоятельно ценный результат.

## 11. Риски

| Риск | Ответ |
|---|---|
| Задание меняется на 30 % в день X, критерии обновляются | текст шагов не зависит от номеров критериев; меняются `Home.md` и шапки |
| Утечка эталона | код живёт только в приватном репозитории, наружу уходят страницы и картинки |
| Мобильный клиент не даёт баллов, но КЗ его требует | минимальная заготовка + прямая оговорка в мануале |
| Скриншоты Windows, а площадка на РедОС | двойные команды + блок отличий на каждой странице |
| AI нельзя для генерации кода (§2 КЗ) | в мануале нет команд «попроси ИИ написать код»; всё пишется руками |
| Запрет Ctrl+C/Ctrl+V при вводе кода на чемпионате | ученик нарабатывает ввод руками на тренировке — это и есть цель курса |

## 12. Критерии приёмки

1. `Home.md` содержит карту критериев: все 17 субкритериев сопоставлены с
   занятиями и страницами, сумма баллов равна 100.
2. Все 24 страницы написаны в согласованном шаблоне.
3. Каждая страница содержит блок «На РедОС 8.0 отличается».
4. ~180 скриншотов и ~30 gif сняты с работающего эталона, подписаны по-русски,
   разложены по `images/`.
5. `tools/judge/` проходит 163 аспекта и выдаёт число баллов по эталону.
6. Эталонный репозиторий не опубликован; в открытом wiki нет кода решения.
7. На `Home.md` есть прямое предупреждение, что курс закрыт на соревнованиях.
